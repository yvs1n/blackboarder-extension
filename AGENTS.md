# Blackboarder

Student companion for Blackboard Learn, built at the University of Sharjah (`elearning.sharjah.ac.ae`) and set up for any university (see University below). It reads announcements and the gradebook, turns them into deadlines and marks, and shows them in a Chrome extension and a phone web app that sync through Firebase.

This file holds what stays true. It has no change log and no bug history: git history has those. Keep it short, and update it in the same commit as any change that makes a line here wrong.

## Commands

```
npm run build     # build everything; also stamps version and test count into README, manifest, companion
npm run lint      # type-check, style, JSON and version-sync checks
npm test          # Vitest
```

Run `npm run lint` and `npm test` before every commit. Commit generated files (`dist/`, `mobile-web/companion/core.js`, stamps) from a fresh `npm run build`. CI regenerates them and pushes a commit to `main`; merge it before pushing.

## What is where

- `src/core/`: courses, schedule, room and weight rules, syllabus data. Single source of truth for course logic. There is no built-in course, schedule or syllabus data: courses come only from the student's saved courses (enrolment list, file import or manual entry).
- `src/engine/`: deadline extraction. Local regex first, then a keyword check, then an optional AI model (no key means the built-in parser's answer stands). The provider (OpenRouter, IFM, or a custom OpenAI-compatible URL) is chosen in `src/engine/aiProviders.ts`; content scripts reach it through the service worker.
- `src/utils/`: storage (`storage/` submodules plus `paymentsStorage.ts` and `semestersStorage.ts` re-exported behind `storage.ts`), Firebase sync, task merge, gradebook marks, marks, GPA and syllabus-progress lists, announcement merge, stream parsing, deletion tombstones (`tombstones.ts`), and common UI helpers (`uiCommon.ts`).
- **Scanning** (`src/scan/`): one set of Blackboard API readers (`blackboardApi.ts`: session, enrolled courses with paging, stream `POST /learn/api/v1/streams/ultra`, course announcements, gradebook; each returns an explicit ok/failed outcome, never a swallowed error) and one pipeline (`scanPipeline.ts`: merge, extraction, marks, repair, save with `saveTasksMergingLatest`, checkpoint) used by both scanners. Every scan goes through `src/background/scanOrchestrator.ts`: the HTTP scan in the service worker (`src/background/httpScanner.ts`) runs first; `scanFallback.ts` decides when the tab scanner takes over (Blackboard unreachable, or the course list and the stream both failed; a signed-out session never falls back, a partial failure only adds a note). The fallback runs in the tab that asked, else an open Blackboard tab, else a background tab the orchestrator opens on `/ultra/stream` and closes afterwards (automatic scans never open a tab). Clicking close (`✕`) on the live scan banner cancels the active scan across background HTTP and tab scanners immediately via `abortScan()`. Blackboard refuses POSTs (the stream) with 403 without the session's XSRF token: both scanners send it as `X-Blackboard-XSRF`, read from the HttpOnly `BbRouter` cookie by the service worker (`src/utils/blackboardXsrf.ts`, `cookies` permission; a tab gets only its own site's token). Course ids come only from the enrolment list and the page; there are no built-in course ids. **Auto-scan** (`autoScanOnPageLoad`): a Blackboard page load asks for a quiet scan at most every 30 minutes (`src/scan/autoScan.ts`, `bbs_last_auto_scan_at`).
- `src/content/scraper.ts`: runs on Blackboard pages and the Banner Student Exam Page (`StudentExamPage`, parsed by `src/core/examSchedule.ts`). It is the tab scanner (`RUN_TAB_SCAN`): the page-only sources (stream cards, announcement cards, the open drawer, classic course pages, the exam schedule table) plus the shared API readers through `bbFetch()`, then the shared pipeline. After a Scan the student starts, the service worker fetches the university's `examSchedulePage` over HTTP with credentials (`src/background/examRefresh.ts`, at most hourly unless a full re-scan, never for automatic scans), and the result joins the scan message (signed out of Banner says so). Each existing exam task takes at most one row, nearest date first, so two midterms keep their own deadlines.
- `src/background/`: service worker (alarms, badge, sync, update checks).
- `src/popup/`: extension popup and side panel (`modules/` for view controllers, `styles/` assembled into `popup.css`, plain TypeScript, no framework).
- `src/mobile/`: `core.ts` is bundled into `mobile-web/companion/core.js` (`window.BBCore`), `app/` parts assemble into `mobile-web/companion/app.js`, and `styles/` parts assemble into `mobile-web/companion/styles.css`.
- `src/userscript/`: standalone iPhone/iPad Safari Userscript (`main.ts`, `scanner.ts`, `storageBridge.ts`, `overlayUi.ts`) compiled by Vite into `mobile-web/blackboarder.user.js` for the free open-source Safari Userscripts extension, scanning Blackboard directly on mobile Safari and pushing to Firebase Vault for the Companion PWA (`blackboarder-android-firefox.zip` / `dist-firefox/` covers Android Firefox, alongside Edge/Quetta mobile extensions).
- `src/worker/`: numbered backend parts assembled by `npm run build` into `mobile-web/_worker.js` and `self-hosted/cloudflare-worker/worker.js`.
- `mobile-web/`: the website. `index.html` is the landing page (whose `#install` section and hero CTA adapt automatically for Desktop, Android, and iPhone/iPad visitors), `blackboarder.user.js` is the Safari Userscript build, `old/` holds the comparison archive of the previous landing page (served with `noindex, nofollow` at `/old/`), `companion/` is the phone app, `og-preview.png` (`1200x630`), `llms.txt`, `robots.txt`, and `sitemap.xml` support SEO/GEO and social previews, and `_worker.js` is the generated sync API and calendar feed (Cloudflare Pages and Vercel).
- `self-hosted/`: the standalone Cloudflare worker (generated from `_worker.js`) and the push reminder cron (`push-cron/`). There is no local Node server.
- `database.rules.json`: Firebase rules. They only take effect once published in the Firebase console.
- `docs/DESIGN_SYSTEM.md`: the visual spec.

## Features and how they work

- **Deadlines**: extracted from announcements (Arabic, English, mixed). Tasks have an id, course, type, due date, weight, room, status, and may carry a mark. When a scanned announcement contains topics/instructions for an assessment, any newly dated assessment is added if absent, while announcements (both dated and undated instructions/topics/rules) matching an existing pending or manual deadline in the same course append their text to the existing deadline without duplicating tasks (`processAnnouncementsBatch`, `findTaskForInstructionAnnouncement`).
- **Payments Management**: `src/core/payments.ts`, `src/core/financePageParser.ts`, `src/utils/paymentsStorage.ts`, `src/popup/modules/paymentsView.ts`, and `src/mobile/app/17-payments.js`. Opened from the header **Payments** button (`#btn-payments-toggle` / `#btn-web-payments`) into `#view-payments`, keeping the 4 main tabs unchanged. Tracks tuition installments and financial deadlines (`PaymentItem`), provides university payment portal links and instructions (`universityPaymentGuide`, verified UOS Banner/Tahseel/SIB links + preset term dates), safely scans open Banner finance summary tables (`parseFinancePageFromDoc`), projects unpaid fees onto Calendar, Deadlines (`#deadlines-payments-strip`), `/feed.ics`, extension notifications, and push reminders without affecting academic GPA, and syncs inside the encrypted Zero-Knowledge Vault (`payments`, `paymentsUpdatedAt`).
- **Marks**: read from the Blackboard gradebook on every scan (`fetchCourseGradebook` in `src/scan/blackboardApi.ts`), plus stream grade cards. A mark goes on a task through `findTaskForUpdate`: the course must agree, practice or mock titles only match each other, numbers must agree (Quiz 1 is not Quiz 10), and a mark never lands on an exam more than a day before its date (homework, lab reports and projects can be submitted and graded early, and are automatically marked done when graded). Unannounced gradebook marks appear in the Grades card as completed items with their official column due date (or empty due date if none), and are never scheduled as deadlines on today's calendar (`purgeSyntheticGradebookTasks` cleans up legacy scan-time tasks and transfers marks to real tasks). The gradebook column is remembered on the task (`gradeSourceId`, `gradeSourcesBefore`). A task with status `submitted` never holds a score, and titles with explicit points must agree with `maxScore` (`sanitizeTaskMarks`). Students can also add manual bonus deadlines or record earned bonus marks (`isBonus: true`, plus `bonusTarget` / `bonusTargetLabel` in Add/Edit Deadline and Bonus modals to pick pure extra marks on `Course Total` even after syllabus percentages or a specific syllabus category), which contribute to `earnedWeight` once graded without inflating required syllabus `gradedWeight`, displaying with a bonus badge and adjusting target GPA requirements.
- **Weights**: from the course syllabus (`resolveTaskWeight`). A percentage in announcement text only counts when it is stated as that item's weight. The title is matched before the body.
- **Rooms**: announced room first, then the saved room if it looks real (`isPlausibleRoom`), then the course schedule.
- **Grades card and Syllabus Progress card** (in the Marks tab in both apps; open or closed is remembered per device): Grades is the projected GPA, then each course's grade with its marks under it, newest first (`src/utils/grades.ts`, built from `buildGpaSummary` and `buildMarksSummary`, ranked newest to oldest by posting, due, or completion date (`dueDate`, `submittedAt`, `completedAt`, `createdAt`), not by when the mark was released; marks for a course that is not set up still show, without a grade). Active courses include interactive Target Grade chips (`src/core/targetGpa.ts`) that compute exact percentage and raw marks required on remaining assessments to achieve desired letter grades. Syllabus Progress is `src/utils/syllabusProgress.ts`.
- **University**: presets in `src/core/universities.ts` (grading scale, Blackboard hosts, built-in quick links; `other` is a generic scale). Only links checked to be right are built in (UOS today). A new install has no quick links; setting the university (picked or detected) swaps in that university's links (`swapUniversityQuickLinks`, from `saveProfile` in the extension and `changeProfile` on the phone), and the "+ Attendance" style buttons fill in only that university's own address (`quickLinkPreset`). The student picks one in the walkthrough or Settings > General > Your University (`src/popup/universitySettings.ts`, phone card `#card-university`), or the first scan sets it from the Blackboard address (`detectUniversityFromHost`). The choice, an edited scale, and discovered student identity (name, ID, email, major, college from `/users/me` and the exam schedule page) are the profile (`src/core/studentProfile.ts`, `bbs_profile`), shown in the Courses tab, the Ultra stream badge (`src/content/studentProfileBadge.ts`), the phone app, and Scriptable widgets, and synced in `data.profile`; the newer `updatedAt` wins. Blackboard addresses that are not built in are added there too: the browser asks for that one site (`optional_host_permissions`) and `src/utils/blackboardSites.ts` registers the scraper and dark mode on it.
- **GPA**: `src/utils/gpa.ts`, on the profile's scale (`profileGradeScale`; UOS when none is set). A course grade is the score on graded items only; a syllabus part with `count` counts only the best `count` items (`outOf` is how many are held; old courses fall back to "best N of M" in the note). Each letter is worth grade points on the scale (shown under each course as "B = 3.0 of 4.0 GPA points"); GPA = sum of points x `creditHours` / credit hours of courses with a mark (a course without it counts as 3; there are no built-in courses).
- **Multi-semester tracking and Cumulative GPA (CGPA)**: `src/core/semesters.ts` (`BBCore` on the phone). Students can snapshot active courses, grades, and schedules at the end of each term into archived semesters (`archiveActiveSemester`), choosing compact (grades and credits) or full snapshot (preserves all tasks and deadlines), and optionally resetting active courses for the upcoming new semester. When Blackboard returns enrolled courses from past years (e.g. Year 1 courses alongside Year 2), `partitionCoursesBySemester` and `autoPartitionPastSemesters` detect Banner term codes (e.g. `_2510`, `_2610`) and seasonal terms, keeping the newest term active and cleanly archiving past completed terms. Term SGPA and Cumulative CGPA are displayed side-by-side in the Grades card (`gradesHtml`), including degree completion progress towards target credits. Prior completed credits, starting GPA, target credit hours, and current term name are configured under Settings > General > Your University (`#details-academic-baseline`), and synced across devices in `data.profile` and `data.semesters`. Past terms can be reviewed read-only in the Marks tab via `#select-semester-view`.
- **Course colours on Blackboard**: Ultra gives each membership a `courseCardColorIndex` and draws class `course-color-N` (N = index % 10 + 1, palette in `src/core/blackboardColors.ts`). The scan registers new courses with that colour (`discoveredCoursesWithColors`); courses already set up keep theirs. `src/content/courseColorPainter.ts` repaints every `course-color-N` element (inline, or `--bbs-cc` plus `data-bbs-cc-before/after` for pseudo-elements, rules in `content.css`) with the student's colour (`findConfiguredCourseHex`), finding the course from the item's own link, else the page's course, else the slot when only one course uses it. Courses not set up keep Blackboard's colour.
- **Activity filter**: `src/content/activityFilter.ts` puts a course and type bar above `.activity-stream` on `/ultra/stream` and hides non-matching `li.stream-item-container` with class `bbs-af-hidden` (Blackboard keeps drawing its list). Course chips are seeded immediately from the student's active courses and Blackboard memberships, excluding non-courses such as `University`, orientation, and sandbox shells (`isExcludedActivityCourse`). When `/ultra/stream` opens, a Swiss Grid preloader (`#bbs-activity-preloader`) covers the stream while courses and initial notification batches preload in the background via Blackboard's `button.load-more-items` and stream scroll nudges, then dismisses automatically. Types come from `classifyActivityItem` in `src/core/activityCategories.ts` (icon, then `guessAssessmentType` on the title and preview). One chip per course name (`activityCourseLabel`). While filtering with few matches or the list end on screen it clicks `button.load-more-items` (disabled while loading and when all are loaded). The choice is saved in `bbs_activity_filter`.
- **Blackboard dark mode**: `src/content/blackboard-dark.js` and `.css`. It never turns on Blackboard's own `mode-dark` (that paints pages #666); rewritten rules are scoped to `html.bbs-dark-active`.
- **Same layout in both apps**: main tabs Calendar, Deadlines, Marks, Courses; Settings sections General, Sync, Calendar, Alerts, Data, Updates in that order (the extension adds Scanning last), with the same card titles and button labels in the same section. `tests/sameLayout.test.ts` checks it; change both apps together.
- **Popup**: opens on the calendar. Unfinished add, edit, Marks, Courses tab and settings work is restored (`src/popup/popupDraft.ts`). Course fields are pickers (`src/popup/coursePicker.ts`). Settings has one page per section. The calendar grid divides its fixed height evenly via `--cal-rows` (`grid-template-rows: repeat(var(--cal-rows, 5), minmax(0, 1fr))`) and maintains the exact same height and width across 4-row (Feb 2027), 5-row (Oct 2026), and 6-row (Nov 2026) months.
- **Marks tab**: student profile badge, semester bar with switcher and archiving tools, Dual-Column GPA Overview with Term SGPA, Cumulative CGPA, discrete combination rounding explanation, and Projected CGPA, Current Term Grades card with all course marks and drops, and collapsible Target Grade Breakdown accordion with trajectory progress bars, momentum trend badges, upcoming score targets, and interactive chips, plus Syllabus Progress breakdown (the popup's `#view-marks`, the phone's `#view-marks`).
- **Courses tab**: one place for each course's name, code, colour, credit hours, class times and rooms, and mark breakdown (the phone's `#view-schedule`, the popup's `#view-courses`), plus quick links. There are no separate read-only schedule or weight cards; everything is edited on the course. Edits sync both ways.
- **Course import & automatic syllabus scan**: Import File reads a syllabus or class schedule (PDF, Word .docx, text or HTML, or pasted text) on the device: `src/core/documentText.ts` (PDF through pdf.js, loaded only then from `vendor/pdfjs/`, which the build copies from `pdfjs-dist`; called with `isEvalSupported: false` for the MV3 CSP), then `src/core/courseDocument.ts` finds courses, class times and assessment weights. With an AI set up, `src/engine/aiCourseImport.ts` asks it first (the extension calls the provider, the phone goes through `/api/ai/extract`) and the built-in result is the fallback. In the extension, `src/scan/syllabusScanner.ts` also inspects enrolled Blackboard course contents/attachments for syllabus files strictly when an AI API key is configured (`resolveAiEndpoint`), running once automatically after the first successful scan (`bbs_first_syllabus_scan_done`) or manually via **Courses > Scan Syllabi** (`#btn-scan-syllabi`), and opening `#modal-course-import` for user confirmation before saving (`openSyllabusReviewFromScan`). The student checks each course before saving (`src/core/courseImportView.ts`); `applyCourseImport` merges into a matching course or adds a new one.
- **Class reminders and today's classes**: `src/core/classSchedule.ts` turns meeting times (local wall clock) into classes. The extension's service worker sets a `bbs_class_reminder` alarm; the phone checks while open and push reminders cover it while closed. Minutes before is `classReminderMinutes` (0 is off). Settings > Calendar > Show My Classes hides the day's classes in the calendar (`showClassesInCalendar` in the extension, `bbs_show_classes` on the phone; per device); the calendar link has its own choice.
- **Calendar feed**: `src/core/calendarLink.ts` makes the link in both apps. `show=deadlines|classes|both` (missing means deadlines, as old links did) and `tz` (IANA zone; class times are converted to UTC from it, DST included). Class events run from a week back to 16 weeks ahead.
- **AI on the web app**: models and keys are set only in the extension. `src/utils/aiKeyLock.ts` sends the key to the student's server (`/api/ai/key`), which encrypts it with `AI_KEY_SECRET` plus the sync key and stores only the encrypted text at `users/{syncKey}/ai`. The web app sends the extension's prompt to `/api/ai/extract` and the server adds the key. AI calls also need the AI pass: the extension makes it, puts it in the pairing link after `#ai=` (never in the query; the phone's sync key box also accepts the whole link, for iPhone home screen apps; the extension also shows it as a QR code (`src/utils/qrCode.ts`) that the phone's **Scan QR** reads with `BarcodeDetector` or the lazily loaded `companion/qr-scan.js` (jsQR, built from `src/mobile/qrScan.ts`)), and the server keeps only its SHA-256 inside the sealed config, so the sync key alone cannot use the AI. Without `AI_KEY_SECRET` or a key, the web app uses the built-in parser.
- **Sync & Zero-Knowledge Vault**: tasks, quick links, courses, the profile, semesters, and tombstones are sealed inside an authenticated, encrypted AES-256-GCM vault envelope (`v1:iv:ciphertext`, derived from the student's secret sync key via HKDF-SHA256, `src/utils/vaultCrypto.ts`, `BBCore` on the phone) before storage at `users/{syncKey}/data` in Firebase, so Firebase administrators and cloud storage never see plaintext academic records. Unencrypted legacy documents are upgraded automatically on the next save. A write replaces the whole object, so every writer reads the cloud copy first (with an ETag; a write that lost the race gets 412 and is merged and retried), merges with `mergeForCloudWrite` (`src/utils/syncMerge.ts`, `BBCore` on the phone) and writes the result; if the read fails nothing is written (the phone queues it). Tasks: the newer `updatedAt` wins per task, and a field the student cleared stays cleared. Tombstones: union. Courses and quick links: the whole list with the newer `coursesUpdatedAt` / `quickLinksUpdatedAt` wins (`bbs_quick_links_updated_at` on both devices); an empty list never beats a full one on a tie. Profile: newer `updatedAt`. Scan request: the newer `requestedAt` wins; for the same request a finished state beats a pending one. The extension reads only `data/scanRequest.json` every minute (`src/utils/cloudScanRequest.ts`), and a pending request older than 15 minutes expires. The sync key field is strictly read-only (`#setting-sync-key`) to prevent typing collisions; generating a new key prompts a confirmation modal (`#modal-regen-key-confirm`) with an instant Export JSON Backup button (`#btn-regen-export-backup`) before resetting. Devices connecting to a deleted or reset sync key unpair cleanly (`unpairSyncKey`) and reset to pairing.
- **Phone app** (`mobile-web/companion/`): phones use a 5-tab bottom bar, and tablet/desktop (`>= 641px`) uses the same 4-tab sections bar (Calendar, Deadlines, Marks, Courses) plus header Settings gear as the extension. At `900px` and wider, Calendar opens a two-column dashboard keeping the compact `496x356` calendar + Up Next on the left beside sticky Deadlines on the right. Settings is split into the same sections as the extension (last one remembered; an unpaired phone opens on Sync). Pairing triggers a post-pairing setup sheet (`#modal-post-pairing-setup`) with immediate toggles for class visibility, push alerts and timing, calendar subscription links, and widget setup.
- **Multi-Platform Widgets & Desktop Companion**: `widgets/`, `windows-widget/`, `src/core/deviceDetection.ts` (`BBCore` on mobile), and `mobile-web/_worker.js`.
  - **iPhone and iPad**: Native frosted liquid glass Scriptable widgets (`widgets/blackboarder-widget.js`) with student ID header, course accent bars, task title and subtitle hierarchy, active task filtering, and completion summary pills. The companion copies a compact one-time loader that downloads `/companion/widget.js` and `widgetConfig` from the website and caches both locally on disk (`blackboarder_cache/`) for automatic styling/content updates and offline use.
  - **Android**: Live Web Widget frosted glass card (`/widget?key=...`) and KWGT Kustom Widget integration (`widgets/android/blackboarder-kwgt.json`, `/api/widget?key=...`).
  - **Windows and Mac**: Windows 11/10 native companion app (`windows-widget/` -> `BlackboarderWidget.exe`, compiled on `windows-latest` and attached to `yvs1n/blackboarder-extension` releases) connecting via personal Sync Key, pulling `profile` + remote `widgetConfig` from `/api/tasks` (cached offline in `tasks_cache.json`), alternating atomic output writes (`lockscreen_widget_a/b.png`, `desktop_widget_a/b.png`), tracking date boundaries and wallpaper mtime changes, and self-updating automatically from `yvs1n/blackboarder-extension/releases/latest` (`SelfUpdater.cs`, `--wait-pid` handoff, UI-thread marshaling via `_uiInvoker`); Mac desktop wallpaper setup via extension Settings > General.
  - **Hardware Detection**: `detectUserDevice` dynamically probes hardware (iPhone model resolution points, Android manufacturer and model user agents, MacBook Pro/Air and iMac screen bounds, Windows PCs) to adapt mobile Settings > Calendar, the post-pairing onboarding sheet (`#modal-post-pairing-setup`), and the extension Settings > General OS companion card (`#settings-page-general`).
- **Push reminders**: the Alerts switch **Push Alerts** (or **Reminders While Closed**) subscribes the phone (`/api/push/subscribe`, stored at `users/{syncKey}/push`, reminders already shown are marked sent). A small Cloudflare Worker with a Cron Trigger (`self-hosted/push-cron/`, every 5 minutes) calls `POST /api/push/tick` (`PUSH_TICK_SECRET`); the **Push reminders** GitHub Action does the same hourly as a backup and by hand; the tick finds subscribed keys with `FIREBASE_AUTH`, sends each due reminder once, encrypted (RFC 8291) and signed with the VAPID keys (`VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`; make them with `node scripts/vapid-keys.js`), and drops subscriptions the push service says are gone. Only known push service hosts are accepted. `companion/sw.js` shows them with the app's tags and the same "already reminded" map (`sidekick-notif-store`).
- **Offline**: `companion/sw.js` caches the app; the root `sw.js` sends offline launches at `/` to it (never make it remove itself). Offline, pasting is off, while done, edit, add and delete save on the phone and mark the queue (`bbs_offline_mutation_queue`); any failed push marks it too, and it is retried on reconnect, on open and every 10 seconds until the server accepts it.
- **Website and SEO/GEO**: the landing page at `/` has Schema.org JSON-LD (`WebApplication`, `WebSite`, `HowTo`, `FAQPage`), `1200x630` OpenGraph/Twitter preview (`og-preview.png`), `llms.txt` for GEO discoverability, and canonical links; `/old/` serves the archived pre-redesign landing page with `noindex, nofollow`. `robots.txt` and `sitemap.xml` are served at the root, and fonts and icons are cached long-term (immutable) by the worker.

The public repo does its own releases (extension zips and `BlackboarderWidget.exe` compiled from `windows-widget/`), and the extension updates itself from it (`EXTENSION_REPO` in `scripts/build.js`, `src/utils/updateChecker.ts`, `updater/`). Never edit the public repo directly. Bump the version for a new release, and keep `export/extension/README.md` current when features change.
- **Store build**: `npm run build` also writes `dist-store/` (and `package` makes `blackboarder-extension-store.zip`) from the same source with `__STORE_BUILD__` true (`IS_STORE_BUILD` in `src/utils/storeBuild.ts`): no updater folder, no `nativeMessaging` or GitHub host permissions, no `initAutoUpdate`, and the Updates page says the store updates it. Upload that zip to the Chrome Web Store and Edge Add-ons; the normal build keeps its helper for people who load it unpacked.
- **Privacy tools**: Settings > Data > Delete My Online Data calls `deleteSyncDataFromFirebase` (removes `users/{syncKey}`) and then makes a new key; Settings > Sync > Download Recovery File saves the key as text. The scan saves `bbs_session_status` (`src/utils/sessionStatus.ts`) from the `users/me` call, and the popup shows a banner while it says the session ended.
- **Performance**: sub-140ms hardware-accelerated CSS view transitions with `prefers-reduced-motion` guards, font preloading (`inter.woff2`, `inter-tight.woff2`), CSS containment (`contain: layout style paint`), 100ms debounced search filtering, and stale-while-revalidate PWA caching.
- **Updates**: managed in Settings > Updates. The extension checks the public repository every 15 minutes using lightweight HTTP without running background processes; when Automatic Updates (`#setting-auto-update`, `bbs_auto_update_enabled`, default on in Settings > Updates) is enabled and the optional updater helper (`updater/`) or a clean `git clone` on `main` is present, new GitHub builds download cleanly (purging old leftover files while skipping locked `updater/host.bat` or unchanged files) and manual **Update now** reloads immediately via `chrome.runtime.reload()`. Without the helper, Settings > Updates offers Check for Updates, Reload Extension, and Download Latest Extension (.zip). A toggleable "What's New" changelog (`#setting-show-changelog`, `bbs_show_changelog_after_update`, `#modal-changelog`) summarizes the latest changes when opening the extension after an update and can also be expanded inside Settings > Updates (`#details-ext-changelog`).

## Rules

1. **Never `fetch('/...')` from the content script.** Blackboard sets `<base href>` to a CDN, so relative paths 404. Use `bbFetch()`.
2. **Never put `\b` around Arabic text in a regex.** JavaScript's `\b` only sees ASCII letters.
3. **Never overwrite tasks the student made or edited** (`userEdited`, `extractedBy: 'manual'`): not their dates, times, rooms, weights or course names.
4. **Save tasks with `saveTasksMergingLatest`** when a save can race a scan, the popup or the phone. A plain `saveTasks` of an older copy can erase marks.
5. **Bump `updatedAt` only when something really changed.** Every bump triggers a sync, and the newer copy wins everywhere.
6. **Real faults use `console.error`; expected situations use `console.info`.** Brave lists every `console.warn` on the extension's Errors page.
7. **Two colours only** (near-black and near-white, plus greys), no gradients, `border-radius: 0 !important`, no em-dashes anywhere. Course colours and the red/amber stats numbers are the only exceptions. Checked by `tests/theme.test.ts` and lint.
8. **Never break sync isolation**: every Firebase read and write is scoped to `users/{syncKey}`. Never write to the root. Sync keys are `BBS-` plus 26 characters (older keys of 8 or more characters still work).
9. **No secrets in the repo.** Never commit the owner's backups, API keys or sync key. The web app never stores an AI key, and the server never returns one. Tests use made-up scores.
10. **Firebase object keys cannot contain `. $ # [ ] /`.** Maps keyed by task id (deletion records) go through `encodeCloudKeys` when written and `decodeCloudKeys` when read, in the extension, the phone app and the worker. Never use an id or title as a key without that.
11. **Course logic lives in `src/core`.** Do not copy it into `src/mobile/app/`; add it to `src/mobile/core.ts` and use `BBCore`.
12. **Scope selectors to their view.** Look classes are shared (the phone's Settings section tabs are `.filter-chip`, like the deadline filters), so a page-wide `querySelectorAll('.filter-chip')` wires the wrong buttons. Use `#view-deadlines .filter-chip[data-filter]` and the like.
