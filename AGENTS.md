# Blackboarder

Student companion for Blackboard Learn, built at the University of Sharjah (`elearning.sharjah.ac.ae`) and set up for any university (see University below). It reads announcements and the gradebook, turns them into deadlines and marks, and shows them in a Chrome extension and a phone web app that sync through Firebase.

This file holds what stays true. It has no change log and no bug history: git history has those. Keep it short, and update it in the same commit as any change that makes a line here wrong.

## Commands

```
npm run build     # build everything; also stamps version and test count into README, manifest, companion
npm run lint      # type-check, style, JSON and version-sync checks
npm test          # Vitest
```

Run `npm run lint` and `npm test` before every commit. Commit generated files (`dist/`, `mobile-web/companion/core.js`, stamps) from a fresh `npm run build`. CI regenerates them and pushes a commit to `main`; merge it before pushing.

## What is where

- `src/core/`: courses, schedule, room and weight rules, syllabus data. Single source of truth for course logic.
- `src/engine/`: deadline extraction. Local regex first, then a keyword check, then an optional AI model (no key means the built-in parser's answer stands). The provider (OpenRouter, IFM, or a custom OpenAI-compatible URL) is chosen in `src/engine/aiProviders.ts`; content scripts reach it through the service worker.
- `src/utils/`: storage, Firebase sync, task merge, gradebook marks, marks, GPA and syllabus-progress lists, announcement merge, stream parsing.
- `src/content/scraper.ts`: runs on Blackboard pages and the Banner Student Exam Page (`StudentExamPage`, parsed by `src/core/examSchedule.ts`). Scans announcements, the Ultra stream (`POST /learn/api/v1/streams/ultra`), linked gradebook assessment columns (`gradebookColumnsToTasks`), the exam schedule table and the gradebook, then saves tasks. After a Scan the student starts on Blackboard (or directly over HTTP from the popup via `src/background/httpScanner.ts` when no Blackboard tab is open), the service worker fetches the university's `examSchedulePage` over HTTP with credentials (`src/background/examRefresh.ts`, zero tabs opened, at most hourly unless a full re-scan, never for automatic scans), and the result joins the scan message (signed out of Banner says so). Each existing exam task takes at most one row, nearest date first, so two midterms keep their own deadlines.
- `src/background/`: service worker (alarms, badge, sync, update checks).
- `src/popup/`: extension popup and side panel (plain TypeScript, no framework).
- `src/mobile/core.ts`: bundled by the build into `mobile-web/companion/core.js` and exposed as `window.BBCore`, so the phone app runs the same logic as the extension.
- `mobile-web/`: the website. `index.html` is the landing page, `companion/` is the phone app, `robots.txt` and `sitemap.xml` for search engines, `_worker.js` is the sync API and calendar feed (Cloudflare Pages and Vercel).
- `self-hosted/`: optional Node server and single-file Cloudflare worker (generated from `_worker.js`).
- `database.rules.json`: Firebase rules. They only take effect once published in the Firebase console.
- `docs/DESIGN_SYSTEM.md`: the visual spec.

## Features and how they work

- **Deadlines**: extracted from announcements (Arabic, English, mixed). Tasks have an id, course, type, due date, weight, room, status, and may carry a mark.
- **Marks**: read from the Blackboard gradebook on every scan (`fetchGradebookUpdates`), plus stream grade cards. A mark goes on a task through `findTaskForUpdate`: the course must agree, practice or mock titles only match each other, numbers must agree (Quiz 1 is not Quiz 10), and a mark never lands on an exam more than a day before its date (homework, lab reports and projects can be submitted and graded early, and are automatically marked done when graded). Unannounced gradebook marks appear in the Grades card as completed items with their official column due date (or empty due date if none), and are never scheduled as deadlines on today's calendar (`purgeSyntheticGradebookTasks` cleans up legacy scan-time tasks and transfers marks to real tasks). The gradebook column is remembered on the task (`gradeSourceId`, `gradeSourcesBefore`). A task with status `submitted` never holds a score, and titles with explicit points must agree with `maxScore` (`sanitizeTaskMarks`).
- **Weights**: from the course syllabus (`resolveTaskWeight`). A percentage in announcement text only counts when it is stated as that item's weight. The title is matched before the body.
- **Rooms**: announced room first, then the saved room if it looks real (`isPlausibleRoom`), then the course schedule.
- **Grades card and Syllabus Progress card** (top of the Courses tab in both apps; open or closed is remembered per device): Grades is the projected GPA, then each course's grade with its marks under it, newest first (`src/utils/grades.ts`, built from `buildGpaSummary` and `buildMarksSummary`, ranked newest to oldest by `gradedAt`, `dueDate`, then `submittedAt`; marks for a course that is not set up still show, without a grade). Syllabus Progress is `src/utils/syllabusProgress.ts`.
- **University**: presets in `src/core/universities.ts` (grading scale, Blackboard hosts, built-in quick links; `other` is a generic scale). Only links checked to be right are built in (UOS today). A new install has no quick links; setting the university (picked or detected) swaps in that university's links (`swapUniversityQuickLinks`, from `saveProfile` in the extension and `changeProfile` on the phone), and the "+ Attendance" style buttons fill in only that university's own address (`quickLinkPreset`). The student picks one in the walkthrough or Settings > General > Your University (`src/popup/universitySettings.ts`, phone card `#card-university`), or the first scan sets it from the Blackboard address (`detectUniversityFromHost`). The choice and an edited scale are the profile (`src/core/studentProfile.ts`, `bbs_profile`), synced in `data.profile`; the newer `updatedAt` wins. Blackboard addresses that are not built in are added there too: the browser asks for that one site (`optional_host_permissions`) and `src/utils/blackboardSites.ts` registers the scraper and dark mode on it.
- **GPA**: `src/utils/gpa.ts`, on the profile's scale (`profileGradeScale`; UOS when none is set). A course grade is the score on graded items only; a syllabus part with `count` counts only the best `count` items (`outOf` is how many are held; old courses fall back to "best N of M" in the note). Each letter is worth grade points on the scale (shown under each course as "B = 3.0 of 4.0 GPA points"); GPA = sum of points x `creditHours` / credit hours of courses with a mark (default 3; a synced course without it takes the default course's value).
- **Course colours on Blackboard**: Ultra gives each membership a `courseCardColorIndex` and draws class `course-color-N` (N = index % 10 + 1, palette in `src/core/blackboardColors.ts`). The scan registers new courses with that colour (`discoveredCoursesWithColors`); courses already set up keep theirs. `src/content/courseColorPainter.ts` repaints every `course-color-N` element (inline, or `--bbs-cc` plus `data-bbs-cc-before/after` for pseudo-elements, rules in `content.css`) with the student's colour (`findConfiguredCourseHex`), finding the course from the item's own link, else the page's course, else the slot when only one course uses it. Courses not set up keep Blackboard's colour.
- **Activity filter**: `src/content/activityFilter.ts` puts a course and type bar above `.activity-stream` on `/ultra/stream` and hides non-matching `li.stream-item-container` with class `bbs-af-hidden` (Blackboard keeps drawing its list). Types come from `classifyActivityItem` in `src/core/activityCategories.ts` (icon, then `guessAssessmentType` on the title and preview). One chip per course name (`activityCourseLabel`). While filtering with the list end on screen it clicks Blackboard's screen reader `button.load-more-items` (disabled while loading and when all are loaded). The choice is saved in `bbs_activity_filter`.
- **Blackboard dark mode**: `src/content/blackboard-dark.js` and `.css`. It never turns on Blackboard's own `mode-dark` (that paints pages #666); rewritten rules are scoped to `html.bbs-dark-active`.
- **Same layout in both apps**: main tabs Calendar, Deadlines, Courses; Settings sections General, Sync, Calendar, Alerts, Data, Updates in that order (the extension adds Scanning last), with the same card titles and button labels in the same section. `tests/sameLayout.test.ts` checks it; change both apps together.
- **Popup**: opens on the calendar. Unfinished add, edit, Courses tab and settings work is restored (`src/popup/popupDraft.ts`). Course fields are pickers (`src/popup/coursePicker.ts`). Settings has one page per section. The calendar grid divides its fixed height evenly via `--cal-rows` (`grid-template-rows: repeat(var(--cal-rows, 5), minmax(0, 1fr))`) and maintains the exact same height and width across 4-row (Feb 2027), 5-row (Oct 2026), and 6-row (Nov 2026) months.
- **Courses tab**: Grades and Syllabus Progress at the top, then one place for each course's name, code, colour, credit hours, class times and rooms, and mark breakdown (the phone's `#view-schedule`, the popup's `#view-courses`), plus quick links. There are no separate read-only schedule or weight cards; everything is edited on the course. Edits sync both ways.
- **Course import**: Import File reads a syllabus or class schedule (PDF, Word .docx, text or HTML, or pasted text) on the device: `src/core/documentText.ts` (PDF through pdf.js, loaded only then from `vendor/pdfjs/`, which the build copies from `pdfjs-dist`; called with `isEvalSupported: false` for the MV3 CSP), then `src/core/courseDocument.ts` finds courses, class times and assessment weights. With an AI set up, `src/engine/aiCourseImport.ts` asks it first (the extension calls the provider, the phone goes through `/api/ai/extract`) and the built-in result is the fallback. The student checks each course before saving (`src/core/courseImportView.ts`); `applyCourseImport` merges into a matching course or adds a new one.
- **Class reminders and today's classes**: `src/core/classSchedule.ts` turns meeting times (local wall clock) into classes. The extension's service worker sets a `bbs_class_reminder` alarm; the phone checks while open and push reminders cover it while closed. Minutes before is `classReminderMinutes` (0 is off). Settings > Calendar > Show My Classes hides the day's classes in the calendar (`showClassesInCalendar` in the extension, `bbs_show_classes` on the phone; per device); the calendar link has its own choice.
- **Calendar feed**: `src/core/calendarLink.ts` makes the link in both apps. `show=deadlines|classes|both` (missing means deadlines, as old links did) and `tz` (IANA zone; class times are converted to UTC from it, DST included). Class events run from a week back to 16 weeks ahead.
- **AI on the web app**: models and keys are set only in the extension. `src/utils/aiKeyLock.ts` sends the key to the student's server (`/api/ai/key`), which encrypts it with `AI_KEY_SECRET` plus the sync key and stores only the encrypted text at `users/{syncKey}/ai`. The web app sends the extension's prompt to `/api/ai/extract` and the server adds the key. AI calls also need the AI pass: the extension makes it, puts it in the pairing link after `#ai=` (never in the query; the phone's sync key box also accepts the whole link, for iPhone home screen apps; the extension also shows it as a QR code (`src/utils/qrCode.ts`) that the phone's **Scan QR** reads with `BarcodeDetector` or the lazily loaded `companion/qr-scan.js` (jsQR, built from `src/mobile/qrScan.ts`)), and the server keeps only its SHA-256 inside the sealed config, so the sync key alone cannot use the AI. Without `AI_KEY_SECRET` or a key, the web app uses the built-in parser.
- **Sync**: tasks, quick links, courses, the profile and tombstones live at `users/{syncKey}/data` in Firebase. A write replaces the whole object, so every writer reads the cloud copy first, merges with `mergeForCloudWrite` (`src/utils/syncMerge.ts`, `BBCore` on the phone) and writes the result; if the read fails nothing is written (the phone queues it). Tasks: the newer `updatedAt` wins per task, and a field the student cleared stays cleared. Tombstones: union. Courses and quick links: the whole list with the newer `coursesUpdatedAt` / `quickLinksUpdatedAt` wins (`bbs_quick_links_updated_at` on both devices); an empty list never beats a full one on a tie. Profile: newer `updatedAt`.
- **Phone app** (`mobile-web/companion/`): phones use a bottom tab bar, 900px and wider is a two-column dashboard. Settings is split into the same sections as the extension (last one remembered; an unpaired phone opens on Sync).
- **Push reminders**: the Alerts switch **Reminders While Closed** subscribes the phone (`/api/push/subscribe`, stored at `users/{syncKey}/push`, reminders already shown are marked sent). A small Cloudflare Worker with a Cron Trigger (`self-hosted/push-cron/`, every 5 minutes) calls `POST /api/push/tick` (`PUSH_TICK_SECRET`); the **Push reminders** GitHub Action does the same hourly as a backup and by hand; the tick finds subscribed keys with `FIREBASE_AUTH`, sends each due reminder once, encrypted (RFC 8291) and signed with the VAPID keys (`VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`; make them with `node scripts/vapid-keys.js`), and drops subscriptions the push service says are gone. Only known push service hosts are accepted. `companion/sw.js` shows them with the app's tags and the same "already reminded" map (`sidekick-notif-store`).
- **Offline**: `companion/sw.js` caches the app; the root `sw.js` sends offline launches at `/` to it (never make it remove itself). Offline, pasting is off, while done, edit, add and delete save on the phone and mark the queue (`bbs_offline_mutation_queue`); any failed push marks it too, and it is retried on reconnect, on open and every 10 seconds until the server accepts it.
- **Website and SEO**: the landing page at `/` has Schema.org JSON-LD (WebApplication, FAQPage), OpenGraph/Twitter cards, and canonical links. `robots.txt` and `sitemap.xml` are served at the root, and fonts and icons are cached long-term (immutable) by the worker.
- **Landing page motion**: `mobile-web/landing-motion.js` (hero fill-in, section reveals, the announcement-to-task typing demo) runs on `mobile-web/vendor/motion.min.js`, a self-hosted bundle of Motion 12 (`animate` from motion/mini and `inView`, exposed as `window.BBMotion`). It does nothing under `prefers-reduced-motion` or on weak devices (deviceMemory 2 or less, 2 or fewer cores, Data Saver); the hero is at least one screen tall below the nav (`--nav-h`), content is visible without it, and it adds only flat, hard-edged effects (clip-path wipes, rises, a count-up). To update the bundle, rebuild it from the `motion` package with those two imports.
- **Reminders**: the app checks while open; `companion/sw.js` also checks on `periodicsync` (registered on the service worker registration; installed Chrome and Edge only) after fetching the sync data URL the app gave it. Both share the "already reminded" map in the `sidekick-notif-store` cache. While the app is closed, iPhones get reminders from push reminders (below) or the calendar feed's alarms.
- **Public repository**: only the extension is public, as `yvs1n/blackboarder-extension` (MIT). `.github/workflows/export-extension.yml` runs after every passing Build, runs `scripts/export-extension.js` (an allowlist; anything new stays private), builds and tests the result, and pushes it with the `EXTENSION_REPO_TOKEN` secret. The public README, AGENTS.md, CLAUDE.md, LICENSE and release workflow come from `export/extension/`; tests that mention private paths (`PRIVATE_TEST_MARKERS`) are not published. The public repo does its own releases (extension zip only), and the extension updates itself from it (`EXTENSION_REPO` in `scripts/build.js`, `src/utils/updateChecker.ts`, `updater/`). Never edit the public repo directly. Bump the version for a new release, and keep `export/extension/README.md` current when features change.
- **Store build**: `npm run build` also writes `dist-store/` (and `package` makes `blackboarder-extension-store.zip`) from the same source with `__STORE_BUILD__` true (`IS_STORE_BUILD` in `src/utils/storeBuild.ts`): no updater folder, no `nativeMessaging` or GitHub host permissions, no `initAutoUpdate`, and the Updates page says the store updates it. Upload that zip to the Chrome Web Store and Edge Add-ons; the normal build keeps its helper for people who load it unpacked.
- **Privacy tools**: Settings > Data > Delete My Online Data calls `deleteSyncDataFromFirebase` (removes `users/{syncKey}`) and then makes a new key; Settings > Sync > Download Recovery File saves the key as text. The scan saves `bbs_session_status` (`src/utils/sessionStatus.ts`) from the `users/me` call, and the popup shows a banner while it says the session ended.
- **Updates**: the extension checks the public repository every 15 minutes; a git clone updates with `git pull --ff-only` through a small helper (`updater/`).

## Rules

1. **Never `fetch('/...')` from the content script.** Blackboard sets `<base href>` to a CDN, so relative paths 404. Use `bbFetch()`.
2. **Never put `\b` around Arabic text in a regex.** JavaScript's `\b` only sees ASCII letters.
3. **Never overwrite tasks the student made or edited** (`userEdited`, `extractedBy: 'manual'`): not their dates, times, rooms, weights or course names.
4. **Save tasks with `saveTasksMergingLatest`** when a save can race a scan, the popup or the phone. A plain `saveTasks` of an older copy can erase marks.
5. **Bump `updatedAt` only when something really changed.** Every bump triggers a sync, and the newer copy wins everywhere.
6. **Real faults use `console.error`; expected situations use `console.info`.** Brave lists every `console.warn` on the extension's Errors page.
7. **Two colours only** (near-black and near-white, plus greys), no gradients, `border-radius: 0 !important`, no em-dashes anywhere. Course colours and the red/amber stats numbers are the only exceptions. Checked by `tests/theme.test.ts` and lint.
8. **Never break sync isolation**: every Firebase read and write is scoped to `users/{syncKey}`. Never write to the root. Sync keys are `BBS-` plus 26 characters (older keys of 8 or more characters still work).
9. **No secrets in the repo.** Never commit the owner's backups, API keys or sync key. The web app never stores an AI key, and the server never returns one. Tests use made-up scores.
10. **Firebase object keys cannot contain `. $ # [ ] /`.** Maps keyed by task id (deletion records) go through `encodeCloudKeys` when written and `decodeCloudKeys` when read, in the extension, the phone app and the worker. Never use an id or title as a key without that.
11. **Course logic lives in `src/core`.** Do not copy it into `mobile-web/companion/app.js`; add it to `src/mobile/core.ts` and use `BBCore`.
12. **Scope selectors to their view.** Look classes are shared (the phone's Settings section tabs are `.filter-chip`, like the deadline filters), so a page-wide `querySelectorAll('.filter-chip')` wires the wrong buttons. Use `#view-deadlines .filter-chip[data-filter]` and the like.
13. **Always bump the version and log changes.** Every update must bump `version` in `package.json`, record changes in `CHANGELOG.md` under the new version header, and commit as `yxsinja <62697781+yas-star@users.noreply.github.com>`. Never commit with bot or AI assistant imprints, and never push changes under an existing version.

## Verifying changes

- Unit tests cover logic. For popup or phone UI, load the built `dist/` popup or `mobile-web/companion/` in a browser with a stubbed `chrome` object and look at it.
- The content script only runs on the owner's signed-in Blackboard. Read-only checks of the gradebook endpoints are fine; never change anything on Blackboard.
